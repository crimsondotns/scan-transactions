# ตัวตน · ข้อมูลในเครื่อง · การแชร์ — สถาปัตยกรรมและข้อจำกัด

เอกสารนี้เป็นผลการตรวจก่อนลงมือ (audit) + แผนที่แปลงแนวคิดจาก Keepit (branch `api`, มีเซิร์ฟเวอร์จริง)
มาเป็นสิ่งที่ทำได้จริงบนเว็บ static ที่ไม่มีแบ็กเอนด์ พร้อมข้อจำกัดที่ต้องบอกผู้ใช้ตรงๆ

## 1. สถานะปัจจุบันของ xcapscan (จากการตรวจซอร์ส)

| เรื่อง | ของจริงวันนี้ |
|---|---|
| ข้อมูลผู้ใช้ | `localStorage` ก้อนเดียว คีย์ `xcap.scan.v1` (`state.v = 2`) = กระเป๋า + settings ทั้งหมด (`src/store.ts`) |
| แคช | `localStorage` แยกก้อน: metadata โทเคน (7 วัน, `src/tokens.ts`), chain list (24 ชม. + คิวล้มเหลว 1 ชม., `src/chains.ts`), ราคา (`src/prices.ts`), สลิปที่เคยออก (`src/slip.ts`) |
| การยิง API | `feed.fetchPage` / `tokens` / `chains` / `prices` → `requestUrl()` → `limitedFetch()` (คิว 2 พร้อมกัน, 429 backoff) |
| ตัวตน/บัญชี | **ไม่มีเลย** — ไม่มี login ไม่มี session ไม่มีโปรไฟล์ |
| การแชร์ที่มีอยู่ | สลิป: `/v/<code>.<data>` — payload อยู่ในพาธ, ตรวจด้วย SHA‑256 (`slipCode`) = ตรวจว่าเนื้อหาไม่ถูกแก้ ไม่ใช่การจำกัดสิทธิ์ |
| deploy | GitHub Actions: install → check → build → upload `dist` → Pages เท่านั้น |
| ความลับ | ไม่มีใน bundle (`pnpm check` + `pnpm check:dist` เป็นด่าน) |

## 2. แปลงแนวคิดจาก Keepit

Keepit บังคับสิทธิ์ที่เซิร์ฟเวอร์ (`src/lib/access.ts` เป็นจุดตัดสินที่เดียว, แถวแชร์ใน Postgres,
ลิงก์เชิญเพิกถอนได้, คนไม่มีสิทธิ์ได้ 404 ไม่ใช่ 403) — สิ่งเหล่านี้ **ต้องมีเซิร์ฟเวอร์ที่เชื่อถือได้**
เว็บ static ไม่มี จึงแปลงได้แค่ "รูปทรงของฟีเจอร์" ไม่ใช่การบังคับ

| แนวคิดของ Keepit | ทำได้บน static ไหม | สิ่งที่แทนได้จริงใน xcapscan |
|---|---|---|
| โปรไฟล์ + username จอง/ไม่ซ้ำ (`username.ts`) | ชื่อ: ได้ / **การจองว่าไม่ซ้ำ: ไม่ได้** (ไม่มีทะเบียนกลาง) | โปรไฟล์ในเครื่อง: ชื่อที่ใช้แสดง + ชื่อย่อ (กติกาตัวอักษรเดียวกับ Keepit) โดยบอกชัดว่า "ชื่อนี้ใช้ในเครื่องนี้/ในแพ็กเกจที่คุณแชร์เท่านั้น" |
| เจ้าของ (owner) | ได้ | ผู้ถือข้อมูลในเครื่องตัวเอง = เจ้าของโดยพฤตินัย |
| ผู้ดู (view) | ได้แบบ "สแนปช็อต" | แพ็กเกจเข้ารหัสที่เปิดแล้วอ่านได้ — แต่ผู้รับคัดลอกต่อได้เสมอ |
| ผู้แก้ไข (edit) | **ไม่ได้ในความหมายเดิม** (ไม่มีข้อมูลกลางให้แก้ร่วมกัน) | ผู้รับแก้ "สำเนาของตัวเอง" แล้วส่งแพ็กเกจกลับให้เจ้าของ merge (คล้าย patch) |
| แชร์ต่อได้/ไม่ได้ (`can_share`) | **บังคับไม่ได้** | เป็นได้แค่คำขอ/ธงในแพ็กเกจ ต้องเขียนใน UI ว่าบังคับไม่ได้ |
| ลิงก์เชิญ + เพิกถอน (`invites.ts`) | สร้างได้ / **เพิกถอนไม่ได้** | ลิงก์แพ็กเกจมีวันหมดอายุที่ตรวจ "ในแอปของผู้รับ" เท่านั้น — ใครเก็บไฟล์/ลิงก์ไว้ก่อนก็ยังเปิดได้ตลอด |
| 404 แทน 403 กัน enumerate | ไม่เกี่ยว | ไม่มีทะเบียนให้กวาด |
| ผู้ใช้หลายเครื่องเห็นข้อมูลเดียวกัน | **ไม่ได้ ถ้าไม่มีที่เก็บภายนอก** | สำรอง/กู้คืนด้วยไฟล์ หรือที่เก็บที่ผู้ใช้เป็นเจ้าของเอง |

## 3. สิ่งที่ยืนยันแล้วว่าทำไม่ได้ (จะไม่ทำให้ดูเหมือนทำได้)

- บังคับสิทธิ์ (ACL) ฝั่งเซิร์ฟเวอร์ — ไม่มีเซิร์ฟเวอร์
- เพิกถอนลิงก์ที่แจกไปแล้ว — ผู้รับถือทั้งข้อมูลและกุญแจอยู่ในมือ
- ตรวจ session ฝั่งเซิร์ฟเวอร์ / ออกโทเคนใหม่เงียบๆ หลังหมดอายุ
- ป้องกันผู้รับคัดลอก/ส่งต่อ/แคปหน้าจอ
- sync ข้ามเครื่องอัตโนมัติโดยไม่มีที่เก็บภายนอกที่ผู้ใช้เลือกเอง

คำที่ **ห้าม** ใช้ใน UI: “Cloud sync”, “Revoke access”, “Private (server enforced)”
คำที่ใช้แทน: “เก็บในเครื่องนี้”, “สำรองเป็นไฟล์”, “แพ็กเกจเข้ารหัสที่คุณส่งเอง”, “ลิงก์นี้ยกเลิกไม่ได้”

## 4. ตัวตน (Google) — ทำได้แค่ไหน

Google Identity Services ออก **ID token (JWT)** ให้หน้าเว็บได้โดยไม่ต้องมี client secret
(Client ID เป็นค่าสาธารณะ ใส่ใน bundle ได้) ใช้ได้บน GitHub Pages รวมถึงกรณีอยู่ใต้ sub-path

สิ่งที่ได้จริง: ชื่อ/อีเมล/รูป/`sub` (id ของบัญชี) สำหรับติดป้ายเจ้าของและเซ็นชื่อบนแพ็กเกจ
สิ่งที่ **ไม่ได้**: ฐานข้อมูล, ที่เก็บ, การตรวจโทเคนฝั่งเซิร์ฟเวอร์, สิทธิ์
ID token หมดอายุ ~1 ชม. และ **ต่ออายุเงียบๆ ไม่ได้ถ้าไม่มีแบ็กเอนด์** → ถือว่าเป็น "ป้ายชื่อ" ไม่ใช่ "ประตู"

ผลที่ต้องยอมรับ: ผู้รับแพ็กเกจ **ตรวจไม่ได้** ว่า “ผู้ส่งคือบัญชี Google นั้นจริง” นอกจากจะมีคนกลางตรวจ JWT ให้
จึงต้องเขียนใน UI ว่าชื่อผู้ส่งบนแพ็กเกจเป็น “ข้อมูลที่ผู้ส่งกรอก/แนบมา” เท่านั้น

## 5. ที่เก็บข้อมูลในเครื่อง

แยกเป็นคลังตามหน้าที่ (identity / profile / appdata / prefs / shares / cache) บน IndexedDB
โดย **ไม่ย้ายของเดิมทิ้ง**: ค่าจาก `xcap.scan.v1` ถูกอ่านมาเติมครั้งแรกแบบ idempotent และ localStorage เดิมยังอยู่จนกว่าผู้ใช้จะสั่งลบ

## 6. การแชร์แบบ static

```
ข้อมูลที่เลือก → JSON → AES-GCM 256 (Web Crypto) → payload
ลิงก์: <base>/s/<id>#<key>     ไฟล์: xcapscan-share.json + กุญแจแยก
```

- กุญแจอยู่ใน fragment (`#…`) ซึ่งเบราว์เซอร์ไม่ส่งไปกับ HTTP request → โฮสต์ static ไม่เห็นกุญแจ
- ถ้า payload ใหญ่เกินใส่ URL → ต้องส่งเป็นไฟล์ (ขีดจำกัดจริงของ URL ~8–32 KB แล้วแต่เบราว์เซอร์/แพลตฟอร์ม)
- วันหมดอายุ/บทบาทที่ระบุในแพ็กเกจ = "คำประกาศ" ที่แอปของผู้รับเคารพ ไม่ใช่การบังคับ

## 7. สิ่งที่ลงมือทำจริง (ไฟล์)

| ไฟล์ | หน้าที่ |
|---|---|
| `src/crypto.ts` | Web Crypto: AES‑GCM 256, กุญแจสุ่ม/กุญแจจากรหัสผ่าน (PBKDF2‑SHA256 250k), base64url, ลายนิ้วมือเนื้อหา |
| `src/local.ts` | IndexedDB (`identity` · `profile` · `shares` · `meta`) + `migrateOnce()` ที่ทำซ้ำได้และไม่ลบของเดิม |
| `src/account.ts` | Google Identity Services (ID token), กติกาชื่อย่อแบบ Keepit, โปรไฟล์ในเครื่อง, `useAccount()` |
| `src/backup.ts` | โครงไฟล์สำรอง, ตรวจไฟล์, `mergeData()` ที่นำเข้าซ้ำแล้วไม่เปลี่ยนอะไร |
| `src/share.ts` | แพ็กเกจแชร์ (บทบาท/หมายเหตุ/วันหมดอายุ + payload เข้ารหัส), ลิงก์ `s/<ซอง>#<กุญแจ>` |
| `src/components/AccountDialog.tsx` | หน้ารวม: ตัวตน · โปรไฟล์ · ข้อมูลในเครื่อง · สำรอง/กู้คืน · แพ็กเกจแชร์ · ข้อจำกัด |
| `src/store.ts` | `snapshot()` / `applySnapshot()` — อ่านและเขียนสถานะทั้งก้อนสำหรับกู้คืน/รวมข้อมูล |
| `scripts/check-dist.mjs` | ด่านหลัง build: ไม่มีความลับใน `dist/` + asset ทุกตัวอยู่ใต้ base เดียวกับ `404.html` |

### ตัวตน

- ปุ่มล็อกอินของ Google ถูกวาดด้วยสคริปต์ของ Google เอง (ไม่มี client secret, ไม่มี redirect ที่ต้องตั้งฝั่งเซิร์ฟเวอร์)
- `client_id` เป็นค่าสาธารณะ: มาจาก `VITE_GOOGLE_CLIENT_ID` ตอน build หรือผู้ใช้วางเองในหน้าบัญชี
- เก็บเฉพาะ `sub`/ชื่อ/อีเมล/รูป/เวลาหมดอายุ — **ไม่เก็บตัว ID token** และไม่มีการต่ออายุเงียบๆ (หมดอายุ → สถานะ “หมดอายุ” ให้กดเข้าใหม่)

### ข้อมูลในเครื่อง

`xcap.scan.v1` (กระเป๋า + ตั้งค่า) ยังอยู่ใน localStorage เหมือนเดิม — ผู้ใช้เดิมไม่ต้องทำอะไรและไม่มีอะไรถูกย้าย
IndexedDB ใช้กับของใหม่เท่านั้น การนำเข้าไฟล์เขียนกลับผ่าน `applySnapshot()` ซึ่งเป็นทางเดียวกับที่ UI ใช้

### การสำรอง

ส่งออกได้ 2 แบบ: JSON ตรงๆ หรือเข้ารหัสด้วยรหัสผ่าน (`{app,kind:'backup-encrypted',salt,payload}` — รหัสผ่านไม่ถูกเก็บที่ไหน)
นำเข้าได้ 2 โหมด: **รวม** (ไม่ลบของเดิม นำเข้าซ้ำได้ผลเท่าเดิม) และ **แทนที่ทั้งหมด**

### การแชร์

`s/<ซองเข้ารหัส base64url>#<กุญแจ>` — ยาวเกิน 6000 ตัวอักษรจะไม่คืนลิงก์ และให้ส่งเป็นไฟล์แทน
บทบาท (ให้ดู / ให้แก้สำเนาของเขาเอง) และวันหมดอายุ เป็น “คำประกาศ” ที่แอปฝั่งผู้รับเคารพ — ไม่ใช่การบังคับ และ **ยกเลิกไม่ได้**

## 8. สิ่งที่ตั้งใจไม่ทำตามของ Keepit

ตารางแถวเชิญ/แถวแชร์ในฐานข้อมูล, `resolveAccess()` ฝั่งเซิร์ฟเวอร์, การตอบ 404 แทน 403 เพื่อกันกวาดชื่อ,
การเพิกถอนลิงก์, การโอนความเป็นเจ้าของ, การจอง username — ทั้งหมดต้องมีเซิร์ฟเวอร์ที่เชื่อถือได้ ซึ่งสเปกนี้ตัดออก
